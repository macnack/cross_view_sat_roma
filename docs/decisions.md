# Decisions log (append-only; date, decision, reason)

- 2026-09-17 — LiDAR is training-only. Inference uses spherical camera + IMU roll/pitch + camera height. Reason: deployment cost; LiDAR teaches geometry, is not needed to use it.
- 2026-09-17 — No dense depth network. BEV built by gravity-aligned IPM; buildings placed by a predicted wall–ground contact line; facade features collapsed onto the footprint; elevated content without ground contact masked. Reason: depth only decides placement; contact line + camera height suffice for orthophoto matching (H2). Raw IPM alone is NOT the method (BevSplat evidence).
- 2026-09-17 — Geometry head on the shared image encoder predicts per-patch normal (gravity frame), planarity, contact line, confidence; labels from LiDAR plane fits. Azimuth encoded as (cos 2α, sin 2α).
- 2026-09-17 — Matcher: Sat-RoMa multi-hypothesis refinement reused; solver 2-point SE(2) RANSAC (scale from camera height), homography as fallback.
- 2026-09-17 — Training losses: Sat-RoMa coarse loss + orientation-aware contrastive alignment on pre-decoder features (hard negatives: same edge orientation within 20 m) + geometry losses. Contrastive term is the main method contribution.
- 2026-09-17 — Lift-Splat (Dur360BEV's SI2BEV) is scaffolding and the learned-lifting ablation row, never the method.
- 2026-09-17 — Kick-off go/no-go: H1 test with LiDAR-oracle BEV and raw IPM BEV on the unchanged Sat-RoMa checkpoint. Small gap → geometry story; large gap → paper is about closing it; neither works → stop.
- 2026-09-17 — Dur360BEV ships no camera↔LiDAR↔INS extrinsics (kick-off page was wrong). Start from SI2BEV's axis permutation; measure residuals on data; lever arm and camera height estimated from data and logged with uncertainty.
- 2026-09-17 — Orthophoto source: Environment Agency VAP (OGL v3) if Durham is covered; Aerial Digimap via a Durham collaborator as fallback (not redistributable). No Google/Bing/Esri tiles.
- 2026-09-17 — Venue: ICCV 2027 if the geometry head transfers to VIGOR, otherwise IROS 2027 / RA-L; deadlines coincide (early March 2027).
- 2026-09-17 — BEV grid: 224×224 cells at 0.25 m (56 m extent, radius 28 m); reference 896 px at the same GSD (224 m). Reason: query must be 224 px for the matcher and 56 m sits inside the checkpoint's 35–70 m training band. Supersedes "radius 40 m".
- 2026-09-17 — Oracle BEV has two variants: (a) LiDAR-only, cells without returns invalid; (b) LiDAR + IPM ground fill where LiDAR has no return. Reason: wet asphalt gives almost no LiDAR returns (frame 0: 27 % return rate, none on the road). Both are reported.
- 2026-09-17 — Camera height: estimated only from frames with road returns (LiDAR ground-plane height) plus the fitted camera–LiDAR z-offset; logged with uncertainty.
- 2026-09-17 — Stored OxTS yaw convention is settled empirically by direction of travel and documented in data/README.md. Device convention per RT3000 manual: vehicle x fwd / y right / z down, heading clockwise from north; Dur360BEV's map_api suggests the files store radians CCW from east.
- 2026-09-17 — environment.yml is for Eagle only; local work uses the existing `bev-patch-pf` conda env.
- 2026-09-17 — Validity mask explicitly excludes the ego-vehicle blind disc and the dual-fisheye stitching seam; extents are logged.
- 2026-09-17 — Dataset subset: the HF release is one 170 GB gzip'd tar ordered by modality, so no sequence-level download exists. We stream it once (scripts/fetch_dur360bev_subset.sh) and keep every 10th frame, dense frames 0–299, all OxTS/timestamps/metadata.
- 2026-09-17 — ERP resolution 1280×640 (source fisheyes are 640 px; Dur360BEV's 2048×1024 default only upsamples).
- 2026-09-17 — Fisheye lens model: use Dur360BEV's piecewise model (196° inner / 203° outer FOV, knee 1.0 rad) from their unused `dualfisheye_project`, not fisheye_tools' ideal 203° equidistant remap. Reason: with identity extrinsics the 196/203 model puts LiDAR points on poles/cars/pedestrians to ~1 px; the 203° remap is ~6 px off at 57° off-axis. Our ERP is now built from this model (`Dur360Frames(lens="dur360")`).
- 2026-09-17 — Camera←LiDAR extrinsic: R = I, t = (0, 0, −0.27) m, i.e. camera 0.27 m above the LiDAR origin. Set visually by Maciej in the overlay viewer; Claude's A/B on near points confirms the sign and |t_z| in 0.13–0.27 m, t_y = −0.03 ± 0.09 m ≈ 0. Automatic edge-score and parallax-regression fits were rejected (both failed an inject-and-recover test). Cross-check by ambient-image↔ERP PnP is pending; value is provisional until then.
- 2026-09-17 — LiDAR height above road 1.57 ± 0.05 m (preliminary, 5 frames; road vs pavement unresolved) → camera height 1.84 m for IPM. Wet asphalt returns almost nothing (median 18 % return rate in road sectors over 275 frames), so this needs re-estimation on drier/better frames.
- 2026-09-17 — Sat-RoMa checkpoint for H1: released `4adxis71` (ACIVS paper: query 35–70 m, ±55°, scale 0.65–1.35), loaded via ~/Github/sat-roma-infer; `checkpoints/satroma_dinov3.pt` does not exist locally.
- 2026-09-17 — Ground handling: LiDAR ground segmentation (local lowest-height floor, 0.5 m cells, ±0.20 m) → per-azimuth contact line v_c(u) = lowest non-ground return per ERP column; IPM is applied only to pixels below v_c(u). Reason: raw IPM smears every above-ground object radially; "no return = ground" leaks on glossy objects. The LiDAR contact line is also the training label the geometry head must later predict, so this variant is the oracle upper bound of the camera-only method.
- 2026-09-17 — Primary kick-off query = "IPM below contact line" (`ipm_cl`: camera geometry + oracle contact line; Maciej: looks best). Reported alongside it: `ipm_raw` (lower bound), `oracle_a` (LiDAR only), `oracle_b` (ipm_cl + LiDAR objects). Known consequence: the query is mostly road surface (17–38 % of the grid valid), so along-road position on straight streets is expected to be weakly constrained.
- 2026-09-17 — ERP validity mask: ego vehicle from 175 moving frames (temporal std < 5 OR |temporal mean of high-pass| > 6, per-column envelope, 6 px margin) = 30 % of the ERP; seams ±1.3° at azimuth ±90°. Ground first visible ≈3.1 m ahead, 1.8 m to the sides, 7.1 m behind (at camera height 1.84 m). File: experiments/00_calib/erp_valid_1280x640.npy.
- 2026-09-17 — Contact line = FOOT of the lowest near-floor return per ERP column (its own x, y dropped to the local floor), not "row of the lowest object return ∩ flat ground". Reason: the bottom 0.2 m of every wall is labelled ground by the tolerance, which overshot contact range by 0.2/1.57 ≈ 13 % (1 m at 8 m); found by a unit test. Only returns < 0.7 m above the floor define a contact, so overhanging canopy/signs do not cut off visible ground.
- 2026-09-17 — Above-contact content is represented as thin WALL EDGES at the contact feet of objects taller than 1.5 m (`ipm_edge`), per Maciej: a wall is a line in a top-down view; its height is irrelevant for matching. The radial "collapsed facade" bands (`ipm_fp`) are rejected (fans; first obstacle only; arbitrary depth) and kept only for the record.
- 2026-09-17 — Multi-frame mosaic: BEVs warped by relative SE(2) pose, nearest-range-wins compositing, edges OR-ed. Poses from KISS-ICP (de-skewed with per-column timestamps) until OxTS is available. 56 m grid coverage at frame 200: 46 % single → 71 % with frames at +1/+5/+10 m.
- 2026-09-17 — Code refactored: parameters in configs/default.yaml, one Makefile target per step, run snapshots in every output folder; rejected calibration fits moved to scripts/attic with reasons.
- OPEN (not yet agreed): (1) patch-validity threshold for the matcher mask — proposed 0.5 primary with 0.25/0.75/no-mask sensitivity (package default 1.0 leaves a median of 10/196 patches); (2) single-frame vs short-mosaic query for H1 — proposed both; (3) wall-edge clutter from trees/poles — proposed LiDAR planarity filter (+ multi-frame vote in mosaics); (4) RANSAC input: published config (one peak per patch) vs distinct GMM means — proposed report both; (5) ambient-image↔ERP PnP cross-check of the camera←LiDAR extrinsic.
