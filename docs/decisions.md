# Decisions log (append-only; date, decision, reason)

- 2026-09-17 — LiDAR is training-only. Inference uses spherical camera + IMU roll/pitch + camera height. Reason: deployment cost; LiDAR teaches geometry, is not needed to use it.
- 2026-09-17 — No dense depth network. BEV built by gravity-aligned IPM; buildings placed by a predicted wall–ground contact line; facade features collapsed onto the footprint; elevated content without ground contact masked. Reason: depth only decides placement; contact line + camera height suffice for orthophoto matching (H2). Raw IPM alone is NOT the method (BevSplat evidence).
- 2026-09-17 — Geometry head on the shared image encoder predicts per-patch normal (gravity frame), planarity, contact line, confidence; labels from LiDAR plane fits. Azimuth encoded as (cos 2α, sin 2α).
- 2026-09-17 — Matcher: Sat-RoMa multi-hypothesis refinement reused; solver 2-point SE(2) RANSAC (scale from camera height), homography as fallback.
- 2026-09-17 — Training losses: Sat-RoMa coarse loss + orientation-aware contrastive alignment on pre-decoder features (hard negatives: same edge orientation within 20 m) + geometry losses. Contrastive term is the main method contribution.
- 2026-09-17 — Lift-Splat (Dur360BEV's SI2BEV) is scaffolding and the learned-lifting ablation row, never the method.
- 2026-09-17 — Kick-off go/no-go: H1 test with LiDAR-oracle BEV and raw IPM BEV on the unchanged Sat-RoMa checkpoint. Small gap → geometry story; large gap → paper is about closing it; neither works → stop.
- 2026-09-17 — Dur360BEV ships no camera↔LiDAR↔INS extrinsics (kick-off page was wrong). Start from SI2BEV's axis permutation; measure residuals on data; lever arm and camera height estimated from data and logged with uncertainty.
- 2026-09-17 — Orthophoto source: Environment Agency VAP (OGL v3) if Durham is covered; Aerial Digimap via a Durham collaborator as fallback (not redistributable). No Google/Bing/Esri tiles.
- 2026-09-17 — Venue: ICCV 2027 if the geometry head transfers to VIGOR, otherwise IROS 2027 / RA-L; deadlines coincide (early March 2027).

- 2026-09-17 — Ground handling: LiDAR ground segmentation (local lowest-height floor, 0.5 m cells, ±0.20 m) → per-azimuth contact line v_c(u) = lowest non-ground return per ERP column; IPM is applied only to pixels below v_c(u). Reason: raw IPM smears every above-ground object radially; "no return = ground" leaks on glossy objects. The LiDAR contact line is also the training label the geometry head must later predict, so this variant is the oracle upper bound of the camera-only method.

Known consequence: the query is mostly road surface (17–38 % of the grid valid), so along-road position on straight streets is expected to be weakly constrained.
- 2026-09-17 — ERP validity mask: ego vehicle from 175 moving frames (temporal std < 5 OR |temporal mean of high-pass| > 6, per-column envelope, 6 px margin) = 30 % of the ERP; seams ±1.3° at azimuth ±90°. - 2026-09-17 — Contact line = FOOT of the lowest near-floor return per ERP column (its own x, y dropped to the local floor), not "row of the lowest object return ∩ flat ground". Reason: the bottom 0.2 m of every wall is labelled ground by the tolerance, which overshot contact range by 0.2/1.57 ≈ 13 % (1 m at 8 m); found by a unit test. Only returns < 0.7 m above the floor define a contact, so overhanging canopy/signs do not cut off visible ground.
- 2026-09-17 — Above-contact content is represented as thin WALL EDGES at the contact feet of objects taller than 1.5 m (`ipm_edge`), per Maciej: a wall is a line in a top-down view; its height is irrelevant for matching. The radial "collapsed facade" bands (`ipm_fp`) are rejected (fans; first obstacle only; arbitrary depth) and kept only for the record.

- 2026-09-19 — Query representation: H1 keeps the RGB BEV. Projecting DINOv3 features into the BEV instead (Maciej's proposal; FG2's design) is deferred to the geometry-head task, where the lifting module is trained. Reasons: (a) the checkpoint's decoder was trained on overhead↔overhead `sat493m` features, and IPM exists precisely to synthesise the nadir view — lifting ERP features would feed it ground-view features against an overhead reference, the cross-view gap FG2 closes by training, so it cannot be evaluated with the frozen checkpoint and it retires H1 ("unchanged matcher"); (b) the lift must be `grid_sample` at sub-patch resolution, never the patch grid: at stride 16 on the 1280×640 ERP only six patch rows see ground (46.8 / 15.5 / 9.3 / 6.5 / 5.0 / 4.0 m, row 21 alone spanning 11.6–23.4 m), which fills 33–56 of the 196 query patch cells and 0 of the 76 cells beyond 20 m (frames 200/1000/2000), whereas one ERP pixel row spans 0.28 m of range at 10 m and 2.1 m at 28 m. The decisive no-training probe — cosine similarity to ortho features at the GT pose, lifted-ground vs BEV-RGB — is blocked on the Durham orthophoto. Injection point when we get there: `f_q_pyramid[16]`, (B, 1024, 14, 14), a single dict in `matcher.py` (the backbone is single-scale; no fine CNN branch).

- 2026-09-19 — BEV attitude stays roll = pitch = 0 for task 01 (Maciej's call, after the cost was measured). - 2026-09-20 — Built `scripts/viz_features.py`: PCA(3)-to-RGB of the raw pre-encoder BEV grid (own colour scale) and of the query tokens f_q vs reference tokens (ONE PCA fit jointly on both, so colours are directly comparable). Located the mode-collapse finding one level deeper: the raw BEV grid (post lift/splat, pre `BevEncoder`) shows real spatial structure matching the LiDAR content (object clusters, road), but the query tokens f_q -- what the decoder actually receives -- are almost perfectly flat/uniform across the 14x14 grid on the step-2000 NLP checkpoint, while the reference tokens (frozen, mature DINOv3 ViT-L) show rich spatial texture on the identical colour scale. This is the direct, one-level-deeper cause of the gm_cls mode collapse: the decoder cannot discriminate where a query patch belongs when the query tokens barely differ from each other in the first place. Points at `BevEncoder` (the small CNN + self-attention compressing 224x224 -> 14x14 into the matcher's feature space) as not yet having learned to encode spatial position, rather than (only) a decoder-training deficit.
